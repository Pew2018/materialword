# 备份与灾难恢复

实现：`lib/services/backup_service.dart`（快照 / 合并 / 原子写入）、
`lib/services/backup_manager.dart`（副本生命周期、自动备份、两种恢复）、
`lib/features/backup/backup_page.dart`（界面）。
测试：`test/phase5_backup_test.dart`（BAK01–BAK21）。

## 备份里有什么

| 内容 | 是否包含 | 说明 |
|---|---|---|
| 词条（含 `phrase` / `examTags` / `bncRank` / `frqRank`） | ✔ | 含删除墓碑 `deletedAt` |
| 词书、词书关联 | ✔ | 关联含 `version` / `updatedAt` / `deletedAt` |
| 学习事件（不可变日志） | ✔ | 恢复后由事件重建 `learning_states` |
| 收藏、用户标签、词条标签 | ✔ | 版本化，删除为墓碑 |
| 字段级版本、身份 aliases | ✔ | 跨设备重命名和字段冲突依赖它们 |
| 共享学习计划与目标 | ✔ | 每日新词、复习上限、学习模式、冲刺计划 |
| 设备设置（主题、强调色、TTS、常亮） | ✔ 仅备份文件 | 协议 v4；**不进入同步数据集** |
| GitHub Token / WebDAV 密码 / 任何凭据 | ✘ | 只在系统安全存储 |
| 系统文件访问令牌、临时路径、活动会话 | ✘ | 属于本机临时状态 |

派生状态（`learning_states`）不单独备份：合并与恢复都会在**同一事务内**由事件重建。

## 协议版本

| 版本 | 内容 |
|---|---|
| v1 | 词条、词书、关联、事件、设置 |
| v2 | 数据集 ID、行/字段版本、关联墓碑、事件 mode、共享/设备设置拆分、内容哈希 |
| v3 | 事件作者日界与来源、收藏、标签、身份别名、字段版本表 |
| v4 | **仅备份文件**可携带 `deviceSettings`；同步数据集仍为 v3 |

导入接受 v1–v4，拒绝更高版本（不猜测语义）。旧版本缺失的可选字段按"未提供"处理，
不会被当成"用户清空"。

## 原子写入

`BackupService.writeBackupFile` / `writeJsonAtomically`：

1. 在同一目录写 `.<name>.tmp`，`flush: true`；
2. **回读**临时文件，长度一致且能被 `decodeDataset` 解析；
3. `rename` 到正式文件名（同目录 rename 在 POSIX 上是原子的）；
4. 失败时删除临时文件并抛出；**从不触碰已有备份**。

文件名形如 `materialword-backup-YYYYMMDD-HHMMSS-SSS-<kind>-<random>.json`，
毫秒 + 6 位随机后缀，同一秒内多次备份不会互相覆盖。

启动时会清理超过 1 小时的 `.tmp` 残留（`BackupService.cleanupTempFiles`）。

**不承诺**所有文件系统都具有相同的崩溃持久性：目录项 fsync 无法用 Dart 的
`dart:io` 表达，因此这里只保证"不会留下半个正式文件"，不保证断电后目录项一定落盘。

## 恢复副本的类型与保留

| 类型 | 何时创建 | 默认保留 |
|---|---|---|
| `manual` | 用户点「立即保存恢复副本」 | 5 |
| `auto` | 自动备份（启动 / 恢复前台 / 每 30 分钟检查） | 5（可配置 1–30） |
| `protective` | 高风险操作前自动创建 | 3 |

自动备份的判定顺序：开关开启 → 距上次自动备份超过间隔（默认 24h）→ 当前内容哈希
与上次不同。**失败不更新成功时间**（下个周期重试），也**不删除**已有副本。

高风险操作（批量删除词条、删除词书、批量重置学习进度、指定版本恢复）在**执行前**
创建保护性备份；备份失败则操作被取消并提示。普通新增、单次作答不触发全量备份。

## 两种恢复方式

### 合并恢复（默认、安全）

`BackupManager.restoreMerge(file)` → `BackupService.mergeDataset`：

- 保留本机所有数据，只补充缺失内容；
- 按 UUID/aliases → normalized 解析身份，事件按 ID 去重；
- 幂等，可重复执行；不会删除本机词条。

### 指定版本恢复（破坏性）

`BackupManager.restoreSnapshot(file)`：

1. 先写一份 `protective` 副本并校验；失败则整个恢复不开始；
2. 校验待恢复文件（`readDataset`）；
3. 在一个数据库事务里：清空可变表（事件、状态、标签、收藏、关联、词条、词书、
   身份别名、字段版本）→ 合并快照 → 重建学习状态；
4. 事务内清理活动会话（`active_study_session_v1`、`active_practice_session_v1`）、
   待重建标记、`sync_target:*`、`sync_auto:*`、`last_sync_*`；
5. 事务内写入"恢复后暂停同步"标记；
6. 事务提交后再应用 `deviceSettings`（可选）。

任一步失败 → 事务回滚，数据库回到恢复前的状态（测试 BAK16 用注入的异常验证）。

### 恢复之后：远端怎么办

恢复不会自动与远端同步，也不会用任一方覆盖另一方。同步页与备份页提供三个明确选择：

- **保持本机状态**：继续暂停，远端不变；
- **合并远端数据**：解除暂停并执行一次正常合并（只增不减，随后上传合并结果）；
- **使用新的同步目标**：改用另一个远端位置。

同步暂停由 `app_meta.sync_paused_after_restore` 表示；`SyncCoordinator.sync()` 在暂停
状态下拒绝执行，自动同步直接返回，直到用户做出上述选择。

## 已知边界

- 恢复期间只依靠单进程互斥：同一进程内的同步、会话、写入会被数据库事务阻塞，
  但没有跨进程/跨设备锁。
- 恢复使用单个事务，20 万级事件时会持有写锁数秒；期间界面应等待，不应同时开始
  其他写操作。
- 本机副本位于应用文档目录，卸载应用会一并删除；重要数据应导出到应用外部。
